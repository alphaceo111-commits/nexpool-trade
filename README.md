### Monetag postback

Rewarded Monetag views fail closed unless the Convex deployment has a server-side `MONETAG_POSTBACK_SECRET`. Do not expose this value to the client or put it in a `VITE_*` variable.

Set the same secret in the Monetag postback URL as the `secret` query parameter (or send it as `x-monetag-secret`). The endpoint is:

```text
https://<your-convex-site-url>/monetag/postback?secret=<MONETAG_POSTBACK_SECRET>&ymid={ymid}&event_type={event_type}&reward_event_type={reward_event_type}&estimated_price={estimated_price}
```

The backend requires `ymid` to match a server-issued challenge, accepts only `valued` / `non_valued` reward events, rejects clicks, checks the Telegram identity when supplied, and credits the verified-ad reward once per ymid. Replayed postbacks are idempotent. The same challenge flow settles task-linked Monetag ads; their configured task reward is credited through the existing task ledger, not a client timer.

Run the postback contract tests with `bun run test`.

Set it from the project Keys/API keys panel or with `bunx convex env set MONETAG_POSTBACK_SECRET <value>` on the intended deployment. Never set production secrets from the client bundle.

If the Mining page shows "Verification unavailable" and the Watch Ad button is disabled, the SDK is loaded but `MONETAG_POSTBACK_SECRET` is not present on the Convex deployment that serves the app. The Operator Console warns about this and reports the real cause. Set the variable on that deployment (add `--prod` for production) and use the identical value in the Monetag postback URL:

```bash
bunx convex env set MONETAG_POSTBACK_SECRET <value>
bunx convex env set --prod MONETAG_POSTBACK_SECRET <value>
```

No progress can be granted without it — the button is disabled on purpose, not by a UI bug.

### Provisioning the production secret

This workspace holds only a deployment-scoped deploy key for the development deployment, so production must be configured with a production-scoped key:

```bash
export CONVEX_PROD_DEPLOY_KEY=...   # deploy key scoped to healthy-hound-245
bash scripts/provision-monetag-production.sh
```

The script fails closed: it exits early if production is already configured, proves the key is authorized for that deployment (HTTP 200 from the deployment API) and that the CLI actually resolves to it, then writes the same value already on development through stdin. It finishes by requiring the public endpoint to answer 403. Neither the key nor the secret is ever printed. The real rewarded-ad check still needs a signed-in Telegram client.

## Telegram publishing

The Operator Console has two publishing paths that share one delivery pipeline (`telegramPosts` + one `telegramDeliveries` row per destination):

- **Composer** — the operator writes and publishes or schedules a post.
- **Automations** — recurring posts generated from confirmed backend records by the templates in `src/convex/publishing.ts`.

Automated posts are code-defined so the copy is reviewable and versioned. `telegramAutomations` stores only configuration and scheduler state: template, destinations, UTC slot, draft mode and the next run. A cron tick every 5 minutes runs due slots through `internal.publishing.runDueAutomations`.

Guarantees that the tests in `src/convex/publishing.test.ts` pin down:

- Every number comes from a confirmed backend record; a template with no data says so instead of inventing ranks.
- The post idempotency key includes the scheduled slot, so a retried or overlapping tick cannot publish the same slot twice.
- Disabled automations publish nothing.
- Delivery state is recorded per chat, so a partial publish is reported as partial rather than published.

Private bot messages use the same pipeline with `kind: "private"`. Telegram only permits a bot to message accounts that started it, so each recipient is its own delivery row and unreachable chats surface as failed rather than being silently dropped. Segments are resolved from real profile state (joined today, never mined, inactive 7 days).

You must follow these conventions when using authentication.

The email OTP configuration is defined in `src/convex/auth/emailOtp.ts`. DO NOT MODIFY THIS FILE.

Also, DO NOT MODIFY THESE AUTH FILES: `src/convex/auth.config.ts` and `src/convex/auth.ts`.

## Using Convex Auth on the backend

On the `src/convex/users.ts` file, you can use the `getCurrentUser` function to get the current user's data.

## Using Convex Auth on the frontend

The `/auth` page is already set up to use auth. Navigate to `/auth` for all log in / sign up sequences.

You MUST use this hook to get user data. Never do this yourself without the hook:
```typescript
import { useAuth } from "@/hooks/use-auth";

const { isLoading, isAuthenticated, user, signIn, signOut } = useAuth();
```

## Protected Routes

The starter `/dashboard` route is protected with `RequireAuth`. Extend that page
for the product's authenticated experience, and reuse `RequireAuth` when adding
another protected route — do NOT hand-roll a redirect to `/auth`, since landing
on a bare sign-in form with no explanation of what was blocked is confusing.

`RequireAuth` states the block on the page the visitor asked for and sends them
to `/auth?returnTo=<current route>` when they choose to sign in, so they come
back to it. Pass `title` and `description` to say what the page is:

```tsx
<Route
  path="/dashboard"
  element={
    <RequireAuth
      title="Sign in to view your dashboard"
      description="Your projects and settings live here."
    >
      <Dashboard />
    </RequireAuth>
  }
/>
```

Pass `redirectImmediately` for a route where bouncing straight to `/auth` really
is better.

## Auth Page

The auth page is defined in `src/pages/Auth.tsx`. Send sign-in and sign-up actions
to `/auth`.

## Authorization

You can perform authorization checks on the frontend and backend.

On the frontend, you can use the `useAuth` hook to get the current user's data and authentication state.

You should also be protecting queries, mutations, and actions at the base level, checking for authorization securely.

## Adding a redirect after auth

The `/auth` route in `src/main.tsx` redirects to `/dashboard` by default. If the
product's main authenticated route is different, update `redirectAfterAuth` to
that route. A validated same-origin `returnTo` query parameter takes priority so
users can resume the protected page they originally requested. Never leave an
authenticated product redirecting back to the public landing page.

## Complete authenticated products

When the requested product implies accounts, a workspace, a dashboard, or other
signed-in functionality, the task is not complete with only a landing page and
auth form. Build the main authenticated experience, protect its route, and verify
that signing in reaches it.

# Using the Convex backend

You will be implementing the convex backend. Follow your knowledge of convex and the documentation to implement the backend.

## The Convex Schema

You must correctly follow the convex schema implementation.

The schema is defined in `src/convex/schema.ts`.

Do not include the `_id` and `_creationTime` fields in your queries (it is included by default for each table).
Do not index `_creationTime` as it is indexed for you. Never have duplicate indexes.


## Convex Actions: Using CRUD operations

When running anything that involves external connections, you must use a convex action with "use node" at the top of the file.

You cannot have queries or mutations in the same file as a "use node" action file. Thus, you must use pre-built queries and mutations in other files.

You can also use the pre-installed internal crud functions for the database:

```ts
// in convex/users.ts
import { crud } from "convex-helpers/server/crud";
import schema from "./schema.ts";

export const { create, read, update, destroy } = crud(schema, "users");

// in some file, in an action:
const user = await ctx.runQuery(internal.users.read, { id: userId });

await ctx.runMutation(internal.users.update, {
  id: userId,
  patch: {
    status: "inactive",
  },
});
```


## Common Convex Mistakes To Avoid

When using convex, make sure:
- Document IDs are referenced as `_id` field, not `id`.
- Document ID types are referenced as `Id<"TableName">`, not `string`.
- Document object types are referenced as `Doc<"TableName">`.
- Keep schemaValidation to false in the schema file.
- You must correctly type your code so that it passes the type checker.
- You must handle null / undefined cases of your convex queries for both frontend and backend, or else it will throw an error that your data could be null or undefined.
- Always use the `@/folder` path, with `@/convex/folder/file.ts` syntax for importing convex files.
- This includes importing generated files like `@/convex/_generated/server`, `@/convex/_generated/api`
- Remember to import functions like useQuery, useMutation, useAction, etc. from `convex/react`
- NEVER have return type validators.
